# 3D that is not built yet

Perspective, cameras, meshes, depth of field, and the default light that are already connected follow [SPEC.md](../../SPEC.md), "Solids and cameras". `<model object>` puts three.js geometry into that scene. What is still missing is picking and author lights.

## Picking

Picking does not paint a PNG. Like `check`, it reads `.layer`, lays out, builds matrices, then answers "which element does this pixel hit". Paint and picking share the same projection and the same flattening rules, so the picture cannot say A while the hit says B.

```ts
pickLayer(source, { x, y }, options?) => {
  hit: { path, id, tag, localX, localY, depth } | null
}
```

`x` and `y` are pixels on the root canvas. y points down. `options` shares file-reading fields such as `baseDir` with `renderLayer`. It does not share `scale`: the point is always in unscaled canvas pixels.

The hit region is the layout box (text includes padding and border, a shape is the shape's box, a line is the box expanded by line width), not the glyph ink. The gap between characters still counts as a hit on that text. `ink` stays for overflow checks and debugging.

Algorithm:

1. Use the same matrix chain as paint, and find every candidate that contains the screen point. The screen point is multiplied by ancestor 2D matrices first. After a layer that opened a camera, it becomes a ray. The ray starts at the viewer and passes through the point.
2. Multiply the ray into the element's local coordinates (the inverse of the parent matrix) and intersect it with the local plane `z = 0`. The hit counts only when the intersection `(localX, localY)` falls inside the layout box. When the matrix cannot be inverted, that subtree has no hit.
3. A flattened subtree no longer compares a child's own `z` with the plane outside. The ray intersects the flattened plane first. After a hit, the topmost child in that plane's 2D result is taken by paint order.
4. When one camera has several hits, take the one with the smallest positive `depth` (closest to the viewer). `depth` is the distance from the intersection to the viewer, in pixels. A difference under 0.5px counts as the same, and then the one later in paint order wins.
5. A hit on the back face is valid. It is not dropped because the normal faces away.
6. An element behind the viewer, an element with `opacity` below 0.01, and the part clipped by `overflow="hidden"` do not take part.
7. When nothing hits, `hit` is `null`. That is not an error.

`path` matches `path` in the report. `localX` and `localY` are local to the layout box, origin at the top-left, for a `<canvas>` or a later editor.

The command sits beside `check` and does not write a picture:

```bash
npx tsx src/cli.ts pick examples/card.layer --at 540,700
```

Standard output is one line of JSON: `{ "hit": { "path": "…", "localX": 12, "localY": 8, "depth": 860 } }` or `{ "hit": null }`. When the source has an **error**-level issue, the exit code is 1, the same as `check`. A miss alone exits 0.

Debug paint (`render --debug`) already traces the four edges of `quad`. Picking itself does not mark the debug picture. To check a point, run `pick` and compare `path`.

Picking for solids (`sphere`, `torus`, `tube`, `model`, and shapes with `depth`) is not decided yet. Flat picking uses the layout box first, not the ink polygon.

## Author lights

The built-in key light and the fixed studio environment are already painted. See `material` in SPEC, "Solids and cameras". Lights specified by the author, and an author environment map, are not. The `shadow` attribute is still an offset dark edge on a plane. It does not follow a 3D light. A model maps material kind, base-color map, vertex color, and emissive onto the existing shading. It does not read three.js lights.

## three.js geometry

The name `Scene3D` is reserved. Do not reuse it. It is not a bitmap viewport.

Painting three.js into one picture and pasting that onto a plane cannot carry internal depth out of the viewport: the mesh cannot cover text outside it, and line art and labels cannot use depth on the model. Flex Layer takes only the geometry and rasters it in its own scene. Occlusion, edge strokes, anchored labels, and frames all use the existing depth buffer.

tsx does not add a tag. The in-memory form of `<model src="hero.glb">` is `object`:

```tsx
import { canvas } from 'flexlayer'
import * as THREE from 'three'

const shape = new THREE.Shape().moveTo(0, 0).lineTo(80, 0).lineTo(40, 60).closePath()
const part = new THREE.Mesh(
  new THREE.ExtrudeGeometry(shape, { depth: 20 }),
  new THREE.MeshStandardMaterial({ color: '#7dce8a', metalness: 0.3 }),
)

export default canvas.create(
  <layer width={800} height={600} camera="fov 30, orbit 30 20">
    <model object={part} unit={1} stroke="#1c1915" hidden="#9a8f80" />
  </layer>,
)
```

`three` is an optional peer dependency. `fromThree` is in `flexlayer/three`. The core does not import `three`. A `.layer` file cannot write an in-memory object. It still uses `src`.

Read these: geometry, the world matrix, material color, roughness, metalness, `DoubleSide`, an in-memory `map`, vertex colors, and `emissive`. `map` tints the base color by uv, then goes through matte, plastic, metal, or glass. `MeshLambertMaterial` and `MeshToonMaterial` use `matte`. `MeshPhongMaterial` uses `plastic`. `shininess` 100 becomes roughness 0, and the environment is sharpest. `MeshPhysicalMaterial` with `transmission` of at least 0.5 uses `glass`. Glass is fake refraction. Otherwise metalness of at least 0.5 uses `metal`, and the rest uses `plastic`. `ShaderMaterial` is not executed. A color in the uniforms is the base color. `material` on the node overrides the whole model.

Not read: shader source, lights, post-processing, normal maps and roughness maps, skeletons, and dashed lines. `SkinnedMesh` uses only the bind pose. `Line`, `LineSegments`, and `LineLoop` become segments and share the depth buffer with meshes. A material with `wireframe: true` keeps only the triangle edges and is no longer painted solid. A line is the material color. Line width is in screen pixels, and the default is 1. `Points` become discs and share that depth buffer. `PointsMaterial.size` is in screen pixels, and the default is 1. `InstancedMesh` expands by instance matrices. Types use `isMesh` / `isLine` / `isPoints`, not `instanceof`.

Coordinates flip only once, at projection. three.js and glb are both y-up. Author space y-down is written in `transformPoint`. A negative linear determinant flips winding, and the adapter swaps triangles back to front-facing.

With no `unit`, each `<model>` is contain-scaled and centered in the wrapping layer. An assembly split into several `<model>` elements writes the same `unit`. The origin sits on that layer's origin (center by default), and world coordinates between parts remain.

Each frame may edit the Object3D and hand it to `<model>` again. The cache hashes geometry content. It does not use the file modification time.

What you can build with three.js: geometry, the math library, the scene graph, `ExtrudeGeometry`, boolean libraries, procedural meshes, and a loader that `readFileSync`s and then `parse()`s. `WebGLRenderer`, shaders, lights, post-processing, and `OrbitControls` do not take part in the picture. A loader that fetches by URL usually needs DOM or `fetch`, and it is not on this path.

R3F components in the browser are not done yet. That would have to detach the rasterizer from `@napi-rs/canvas` and `node:fs`.
